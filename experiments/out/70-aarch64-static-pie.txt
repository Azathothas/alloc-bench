=== what this establishes ===

 static-PIE is decided by ONE BOOLEAN IN RUSTC, not by the linker.

   x86_64-unknown-linux-musl  sets static-position-independent-executables
   aarch64-unknown-linux-musl leaves it unset

   so rustc emits -static -no-pie on the aarch64 link line and
   -static-pie on the x86_64 one.

 BOTH targets already use the gnu-cc linker flavour -- the gcc
   driver. So 'use gcc instead of rust-lld' is not a lever: it is
   already what happens. The previously recorded reason ('rust-lld
   rejects the argument') does not describe this.

   -C link-arg=-static-pie only APPENDS the flag; rustc's own
   -static -no-pie stay on the line beside it.

RESULT: exit 1 ON PURPOSE. The project publishes aarch64/musl
static-pie* cells as unsupported with this reason, and runs `core`
on the non-PIE static-lto profile there. docs/history/todo/platform.md T-002.

=== what this probe cannot tell you ===
- whether the aarch64 musl LINKER would accept -static-pie if asked.
  rustc never asks, and this host has no aarch64 cc to ask it with.
- whether a CUSTOM target JSON with the flag flipped, built with
  -Z build-std, would produce a working static-PIE. Untested, and it
  would mean shipping a custom rustc target.
 So 'impossible' is not what this says. 'Not achievable from the
  stable toolchain as it stands' is.
