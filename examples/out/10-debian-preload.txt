=== 4.  THE SILENT FAILURE, PLANTED ON PURPOSE ===
A path that does not exist. Watch the program succeed anyway: this is
what 'I set LD_PRELOAD and my benchmark got faster' looks like when the
library was never loaded. The residency check is what tells them apart.

  LD_PRELOAD=/usr/lib/libthis-does-not-exist.so ./allocprobe count 500
    exit status: 0          <-  SUCCESS. The loader did not fail.
    stdout:      COUNT planted=72 found=72
    stderr:      ERROR: ld.so: object '/usr/lib/libthis-does-not-exist.so' from LD_PRELOAD cannot be preloaded (cannot open shared object file): ignored.
   control: libthis-does-not-exist.so is absent without LD_PRELOAD (so the check above can fail)

   The loader writes a line to stderr and carries on. A program that
     does not read its own stderr -- which is most of them, under a
     supervisor -- reports nothing at all. Check residency, not exit codes.

=== 5. the system-wide version, and why to be careful with it ===
/etc/ld.so.preload applies to EVERY dynamically linked program on the
system, with no environment variable to forget. It is the closest thing
to literally 'replacing the system's allocator'.

  # echo /usr/lib/x86_64-linux-gnu/libjemalloc.so.2 > /etc/ld.so.preload
   ls, an unrelated system binary, under the system-wide preload -> exit 0: bin boot dev etc examples home lib lib64 media mnt opt proc root run sbin srv sys tmp usr var
   libjemalloc.so.2 is mapped into the running process (LD_PRELOAD took effect)
  # rm /etc/ld.so.preload      <- restored

   IF THE LIBRARY IS BROKEN, EVERYTHING IS BROKEN, including the shell
     you would use to undo it. Test with LD_PRELOAD in one process first,
     and on a real machine keep a second session open before writing that
     file. In a container image it is safe: the blast radius is the image.

=== what this example establishes ===
 A dynamically linked binary can be given a different allocator with no
   rebuild, and the replacement can be PROVEN to be in the process.
 It does not establish that it is faster. NOT ONE preloaded allocator
   this project has measured has beaten glibc's own on Debian: five of
   six are slower and the sixth ties, in
   results/published/2026-09-03-preload-x86_64-all-eight/.
 It says nothing about musl. See examples 30 and 40.
